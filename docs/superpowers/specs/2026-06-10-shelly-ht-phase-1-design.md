# Shelly H&T Gen3 Integration — Phase 1 Design

## Context

Long-term goal: replace the ESP32 + BME688 + light-sensor setup with off-the-shelf Shelly H&T Gen3 (battery-powered Wi-Fi temperature & humidity sensor). This is a multi-phase migration:

- **Phase 1 (this spec):** Add Shelly support alongside ESP32. Both sources feed the same sensor stream. No user-visible regressions.
- **Phase 2 (later spec):** Strip light/pressure/CO2 from home, plants, digest, alerts, smart tips.
- **Phase 3 (later spec):** Decommission ESP32 path and firmware.

## Goal

A Shelly H&T Gen3 device, paired through the app and configured with a generated webhook URL, posts temperature and humidity into the existing `SensorData` stream. ESP32 keeps working unchanged.

## Out of scope

- Stripping or modifying any existing light/pressure/CO2 UI (Phase 2).
- Removing the ESP32 REST endpoint or firmware (Phase 3).
- Battery-low and device-offline alerts (data is captured but no alerting yet).
- A "which device am I looking at" multi-device UI.
- Shelly Cloud / OAuth integration.

## Architecture

### Webhook endpoint

```
POST /api/shelly/webhook?token=<userToken>&deviceId=<shellyDeviceId>&t=<tC>&h=<rh>&bat=<battPercent>
```

- **Method:** GET-style query parameters delivered via POST (no body required). Shelly Gen3's URL Actions feature supports placeholder substitution in the URL itself, so the user pastes one templated URL into Shelly's web UI and Shelly does the rest. No JSON parsing of Shelly's schema is required on our side.
- **Required params:** `token`, `deviceId`, `t`, `h`. Battery (`bat`) is optional — older firmware or non-battery models may not emit it.
- **Auth:** `token` is a 32-byte random opaque string per Shelly device, generated by GrowWatch at pairing time. The backend looks up `ShellyDevice` by `webhookToken` to identify both the user and which device. No JWT — Shelly cannot refresh.
- **Response:** `204 No Content` on success. `401` if token is unknown. `400` if required params are missing or not numeric.
- **Rate limit:** 1 request per device per 10 seconds. Shelly under normal operation reports far less often than that; this caps misconfigured devices and basic abuse.

### Mongo model: `ShellyDevice`

```ts
{
  _id: ObjectId,
  userId: string,          // owner (claimed at pairing time)
  deviceId: string,        // Shelly serial e.g. "shellyhtg3-AABBCCDDEEFF" — unique per user
  name: string,            // user label, e.g. "Greenhouse"
  webhookToken: string,    // 64-hex random, indexed for webhook lookup
  lastSeenAt: Date | null,
  lastBatteryPercent: number | null,
  createdAt: Date,
}
```

- Indexes: `webhookToken` (unique), `(userId, deviceId)` (unique).
- Stored separately from the existing ESP32 `Device` model. The two pairing flows have different fields and different lifecycles; conflating them would require null-everywhere or discriminator fields. Keeping them separate is cleaner.

### Data flow into the existing pipeline

The webhook handler does exactly this:

1. Look up `ShellyDevice` by `webhookToken`. 401 if not found.
2. Parse `t` and `h` as floats. 400 if missing or non-numeric.
3. Update `lastSeenAt = new Date()` and `lastBatteryPercent = bat` (if present).
4. Call the existing `handleSensorData({ temperature: t, humidity: h })`. `lightLevel`, `pressure`, `co2` left undefined.
5. Return 204.

`handleSensorData` already publishes to `sensorDataStore` (in-memory), triggers the GraphQL subscription, and feeds the hourly aggregator. Nothing else needs to change in the data pipeline.

### Pairing UI

New page at `/settings/shelly-setup`, mounted alongside the existing `/settings/sensor-setup`. Layout mirrors the ESP32 setup page (same modal patterns, same `shadow-gw-sm` cards).

- **List view:** paired Shelly devices, each row showing name, deviceId (truncated), `lastSeenAt`, battery %, with kebab → Rename / Rotate token / Remove.
- **Add device flow** (one card with inline form):
  1. User enters device ID (the Shelly serial visible on the device's web UI or its label) and a display name.
  2. App POSTs `addShellyDevice` mutation → backend generates `webhookToken`, returns the new device + the ready-to-paste webhook URL.
  3. UI shows the URL with a Copy button and a one-screen instruction: *"In your Shelly's web interface → Settings → Webhooks → Add → paste this URL. Use trigger: temperature change ≥ 0.5°C OR humidity change ≥ 2%."*
- **Rotate token:** if the user feels their URL leaked. Generates a new token; old one stops working immediately.

### GraphQL

```graphql
type ShellyDevice {
  id: String!
  deviceId: String!
  name: String!
  webhookUrl: String!         # full URL including current token + placeholders
  lastSeenAt: String
  lastBatteryPercent: Int
  createdAt: String!
}

type Query {
  myShellyDevices: [ShellyDevice!]!
}

type Mutation {
  addShellyDevice(deviceId: String!, name: String!): ShellyDevice!
  renameShellyDevice(id: String!, name: String!): ShellyDevice!
  rotateShellyToken(id: String!): ShellyDevice!
  removeShellyDevice(id: String!): Boolean!
}
```

`webhookUrl` is a computed field that emits the full templated string with placeholders for Shelly to substitute. The exact placeholder syntax is verified against a real Gen3 device during implementation; if Shelly's Gen3 syntax turns out to differ from `${ev.tC}` / `${ev.rh}` / `${devicepower:0.battery.percent}`, the resolver's template string is adjusted — no schema change needed.

### Auth requirement

All four mutations and the query require an authenticated user (JWT in cookie, same as every other authed resolver). The webhook itself is unauthenticated at the HTTP layer; auth is enforced by token lookup.

### Token format

64 hex characters (32 bytes from `crypto.randomBytes(32)`). Stored as-is. Compared with constant-time equality (Mongo lookup is fine — it doesn't time-leak per-character).

## What stays untouched

- ESP32 `/api/sensor-data` REST endpoint and `Device` model.
- `handleSensorData` and the in-memory sensor store.
- Home page, plants, light page, digest, alerts, smart tips, all subscription logic.
- Existing settings tabs.

## Risks

- **Per-device webhook token in URL is shared-secret in a query string.** Acceptable: payload is non-sensitive (room temperature). Mitigation: tokens are 32 bytes random, rotatable in one click, rate-limited per device. Webhook is `https` only (rejected `http` requests via the Vercel proxy).
- **Multiple Shellys per user might report the same temperature into the shared `sensorData` stream**, with no UI distinction in Phase 1. That's an explicit deferral to Phase 2. Users with two Shellys in Phase 1 will see interleaved readings; users will be told to pair only their primary device until Phase 2 ships.
- **Shelly Gen3 placeholder syntax** is the one externally-verified piece. The template string we emit must match Shelly's documentation. If wrong, the webhook URL is silently broken on Shelly's side. Implementation must verify against a live device before declaring done.

## Success criteria

- A user can navigate to `/settings/shelly-setup`, click "Add device", paste device ID + name, receive a webhook URL, and copy it.
- Pasting that URL into a real Shelly Gen3's outbound webhook (with placeholder substitution enabled) results in temperature and humidity readings appearing in the existing home page within one minute of the device reporting.
- The home page shows live updates exactly as it does for ESP32.
- Removing or rotating the token causes Shelly's subsequent posts to be rejected with 401.
- No existing ESP32 flow is broken.
